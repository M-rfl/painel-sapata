## Schema decisions (resolved open question; state in SUMMARY)

- **`source_runs`** is a TOP-LEVEL key, a peer of `sentido_runs`. It is the RLE `[[start_row, source_index], ...]` of `run.origin[i][0]`, where `source_index` indexes `meta.source.files`. Run 1: `[[0, 1], [10839, 0]]`. "Region k" = the k-th run in time order (the engine numbers regions by first appearance).
- **`meta.workbook_reference`** is present only when the converter runs with `--golden`:
  ```json
  { "source": "<golden['oracle'] or 'golden'>",
    "thresholds_g": [0.5, 1, 2, 4],
    "medians_lsb": [...], "class_counts": [...], "eventos": N, "impactos": N, "impacts_by_class": [...],
    "sentido_basis": "source_file_time_order",
    "sentido_records": [10839, 12544], "sentido_eventos": [1262, 1090] }
  ```
  KPI keys come from `golden["exact"]`, and `sentido_records` / `sentido_eventos` from `golden["reference"]`, copying only keys that exist. `thresholds_g` comes from `meta.workbook_defaults`. If none of `class_counts`/`eventos`/`impactos`/`impacts_by_class` exists in the golden, return None so that the key is omitted (the engine then reports "not available").
- The schema stays 1 (additive optional keys). The JS must tolerate both keys being missing.
- `cli.py` keeps calling `reference_analysis` with the 5 positional args. At defaults the time-jump split gives identical numbers (plan 10-01 asserts this), so no oracle change is needed here and this plan stays independent of 10-01.
